### 📌 Описание проекта
Реализация распределенного кэширования по паттерну **Cache-Aside** на базе высокопроизводительной СУБД **Redis** и платформы **.NET 9 (C#)**.

#### Предметная область варианта 9:
* **Задача:** Мониторинг безопасности серверной инфраструктуры и кэширование данных CVE-уязвимостей.
* **Ключ в Redis:** `vulns:server_01`
* **Время жизни кэша (TTL):** 5 минут
* **Полиморфные модели:**
  * `VulnerabilityEvent` — базовый абстрактный класс события безопасности;
  * `VulnerabilityDetectedEvent` — событие обнаружения уязвимости с уровнем критичности (`Severity`: CRITICAL, HIGH);
  * `VulnerabilityPatchedEvent` — событие устранения уязвимости с фиксацией идентификатора патча (`PatchId`).

### 🏗️ Архитектура и паттерн Cache-Aside
1. **Интерфейс кэширования:** `ICacheProvider` (`GetAsync`, `SetAsync`) изолирует логику приложения от конкретного хранилища.
2. **Провайдер Redis:** `RedisCacheProvider` реализует работу с Redis через библиотеку `StackExchange.Redis`.
3. **«Дорогая операция»:** `VulnerabilityScanner.ScanServerAsync` имитирует длительное сканирование инфраструктуры (задержка 3000 мс).
4. **Алгоритм работы:**
   * **Cache MISS (промах кэша):** при первичном запросе данные отсутствуют в Redis $\rightarrow$ выполняется сканирование (~3008 мс) $\rightarrow$ результат сериализуется в JSON и сохраняется в Redis с TTL 5 мин.
   * **Cache HIT (попадание в кэш):** при повторном запросе данные мгновенно извлекаются из памяти Redis за **12 мс**, а экземпляр сканера не создается (ускорение >250 раз).

### 🐳 Запуск через Docker и Docker Compose

```bash
# 1. Сборка и запуск контейнеров в фоновом режиме
docker compose up -d --build

# 2. Проверка статуса контейнеров
docker compose ps

# 3. Запуск приложения в интерактивном режиме
# Режим 1: с кэшем (Cache-Aside)
# Режим 0: без кэша (прямой запрос)
docker compose run --rm cache-app

# 4. Остановка и удаление контейнеров
docker compose down
```
